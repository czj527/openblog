# 开发协作基础设施

> 这个目录存放**开发协作所需的规范、契约与工单**。
> 不是产品文档，不是营销材料，是给开发 Agent 看的执行依据。

---

## 为什么有这个目录

AI 时代的项目失控，通常不是"做不出来"，而是：

1. **spec 写错** → agent 很自信地交付 2000 行错代码
2. **无法验证** → agent 说"已完成"，你没法 5 分钟确认
3. **决策堆积** → 你不知道今天该拍板哪几件事

所以这里的结构围绕这三件事设计。

---

## 目录结构

```
docs/
├── 00-overview.md          ← 项目总览（这是什么、边界在哪）
├── 01-spec/                ← 【计划层】要做什么。会变，git 记录每次变化
│   ├── architecture.md     ← 目标架构
│   ├── data-model.md       ← 数据模型与职责边界
│   └── auth.md             ← 权限方案
├── 02-contracts/           ← 【契约层】不可违反的硬约束
│   └── design-system.md    ← 视觉基线（原 DESIGN.md）
├── 03-tickets/             ← 【执行层】工单，可变、可作废、可重开
│   ├── T0-security.md
│   ├── T1-slimming.md
│   ├── T2-data-layer.md
│   ├── T3-permissions.md
│   ├── T4-notion-cms.md
│   └── T5-economy-and-legal.md
├── 04-acceptance/          ← 【验收层】怎么确认做对了
│   └── checklist.md
└── 05-migration/           ← 【历史】旧项目现状与迁移记录
    └── legacy-audit.md
```

**三层分离的核心：变更只发生在最底层。**

| 层 | 变动频率 | 谁来改 | 怎么留痕 |
|---|---|---|---|
| 01-spec 计划层 | 月度 | 陈 + 蓝 | git diff |
| 02-contracts 契约层 | 极少 | 陈（视觉基线） | git diff + 明确同意 |
| 03-tickets 执行层 | 每天 | 蓝 | 状态翻转 + 作废重开 |

需求变化时：**改 spec → 作废旧工单 → 重开工单**。上层不复制下层内容，只引用。

## 给开发 Agent 的阅读顺序

```
1. docs/00-overview.md              ← 先看这个，理解全局与边界
2. docs/02-contracts/design-system.md ← 硬约束，必须遵守
3. docs/01-spec/*.md                ← 理解目标状态
4. docs/03-tickets/                 ← 按顺序执行
5. docs/04-acceptance/checklist.md  ← 交付前自检
```

---

## 硬性规则（不可协商）

1. **视觉是最高优先级。** `02-contracts/design-system.md` 是项目所有者已认可的基线。任何"看起来更好"的改动都可能是他不想要的 —— 不确定就不要改。
2. **不得修改** `design-system.md`、`src/components/ui/`、`globals.css` 中的色彩令牌。
3. **删除文件前必须全局搜索引用**，确认无残留 import。
4. **每个工单必须提供验收证据**：构建日志、页面截图、curl 返回示例。**不接受口头"已完成"。**
5. **每个工单一个 commit**，格式：`[T{n}] 简述`。
6. **遇到需要产品决策的情况，停下来问，不要自己猜。**
7. **URL 结构不得变化** —— 这是 SEO 底线。

## 状态约定

工单状态只有五种，不要发明新的：

| 状态 | 含义 |
|---|---|
| `待开工` | 依赖已满足，可以开始 |
| `进行中` | 有人在做 |
| `待验收` | 已完成，等陈验收 |
| `已验收` | 陈签字通过 |
| `已作废` | 需求变了，不要再做（写明作废原因和替代工单） |

> **暂停** 的项目/工单必须显式标记，不要留在"进行中"。同时进行的主攻项目不超过 2 个。
