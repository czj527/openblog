## 一、已经确认的项目边界

以下事项已经由项目所有者确认，不再作为待决策项：

1. `openblog` 是唯一正式开发仓库。
2. `portfolio` 保留，不继续在其上开发。
3. 正式迁移基线为 `portfolio origin/main`；`portfolio` 当前本地未提交修改只作参考。
4. 只迁移经过白名单确认的视觉、组件、主题和静态资源。
5. 新文章以 Notion 为唯一内容源，站点不再提供本地文章编辑器和 AI 写作面板。
6. 经济规划页第一版完全私有，仅管理员可见。
7. 已发布文章的 Slug 默认不可修改；确需修改时，保留旧 Slug 的 301 或别名。
8. 评论、点赞等互动数据不能使用 Slug 作为长期关联键，应使用稳定的 Notion page ID 或内部 `post_id`。

## 二、必须先修正的严重问题

### 1. T0/T1 的执行对象错误

当前 `openblog` 只有规划文档，没有 `src/`、`package.json`、锁文件、Next.js 配置或 Supabase migration。现有 T0/T1 却直接要求重写或删除旧仓库中的文件，例如：

- `src/lib/auth.ts`
- `src/app/api/clear-data/route.ts`
- `src/app/api/supabase/route.ts`
- `src/app/ai-write/page.tsx`
- `prisma/`
- `src/components/blog-agent/`

这些路径属于 `portfolio`，不属于 `openblog`。因此不能直接执行旧 T0/T1，必须新增“项目初始化与资产导入”阶段。

### 2. D1 已经过时

`DECISIONS.md` 已确定 `openblog` 独立重构，但 `TASKS.md` 仍在询问“在 `portfolio` 改造还是在 `openblog` 重写”。D1 应改为已完成，内容应明确：

> 正式代码全部在 `openblog`；`portfolio origin/main` 只读提取视觉、组件、静态资源和历史数据。

### 3. 迁移白名单没有冻结

“保留部分前端”不足以指导实现。开工前必须列出：

- `globals.css` 是否整体迁移；
- `components/ui` 迁移哪些组件；
- `components/effects` 迁移哪些组件；
- 是否保留季节主题、天气主题和天气 API；
- 是否保留项目、路线图、任务、日程页面；
- 图片、字体、头像等静态资源如何处理；
- 哪些业务逻辑全部重写；
- 哪些旧页面、接口和依赖明确废弃。

应采用 allowlist 迁移，禁止复制整个旧项目后再依靠删除清理边界。

### 4. 旧数据模型没有完成映射

旧站的页面、接口和数据表并不是一套统一模型：

- `/projects` 使用的字段与 Supabase 项目种子字段不一致；
- `/api/projects` 仍依赖 Prisma；
- `/project-logs/[id]` 使用 `project_logs`，目标模型未定义该表；
- `/roadmap` 依赖多张 `workflow_*` 表，目标模型未定义这些表；
- `/tasks` 和 `/schedules` 的旧接口存在直接使用 service role 的路径，管理员鉴权不完整；
- 旧留言数据有 `email` 字段，目标 `guestbook` 模型没有对应字段。

必须先决定页面是否保留，再建立字段映射和数据迁移清单。不能把“删除 Prisma”当成数据库迁移方案。

### 5. 公开写入、RLS 和管理员鉴权相互冲突

现有文档同时要求匿名用户评论、点赞、留言，允许匿名角色直接插入，又要求所有写操作使用 service role，并要求 T3 的写接口先 `verifyAdmin`。

建议统一成以下规则：

- 浏览器使用 anon key 读取公开数据；
- 所有公开写入都经过 Next.js API Route；
- API Route 负责输入校验、HTML 清洗、限流和审核状态设置；
- 服务端使用 service role 写入；
- 管理员专属接口才要求 `verifyAdmin`；
- Supabase anon 不直接开放评论、留言等写权限。

### 6. 内存 Map 不能作为生产级全局限流

Vercel 函数实例可能冷启动、扩缩容或并行运行，单进程内存计数不能提供稳定的全局限流。

建议登录限流使用 Redis、Upstash 或 Vercel KV。评论和留言可以先使用数据库记录加盐哈希后的 IP，但必须明确哈希盐、用途、保留周期和隐私政策说明。

### 7. Notion 版本、Webhook、缓存和图片策略尚未冻结

现有文档把 `2025-09-03` 写成当前 Notion API 版本，同时只设计了自定义 secret 校验和简单缓存。实现前需要重新核对官方接口，并明确：

- 采用并固定的 API 版本；
- data source 查询方式；
- Webhook 验证 token 和事件签名校验；
- Webhook 失败后的 ISR 或定时重新验证兜底；
- Notion 临时图片 URL 的代理、刷新或稳定存储方案；
- 同步延迟验收是“最终一致”还是固定时间上限。

不能只配置 `next/image` 的远程域名。Notion 托管图片本身存在过期问题，必须设计 URL 刷新或图片迁移方案。

### 8. Next.js 版本与缓存写法没有对齐

计划选择 Next.js 16，却同时使用 `unstable_cache`、旧式 `revalidateTag('posts')` 和 ISR。应先冻结缓存模型，再统一实现方式、tag 命名、失效调用和验收标准。不要在不同文档里混用新旧缓存 API。

### 9. Slug 验收规则与已确认决策冲突

当前验收要求修改 Slug 后旧 URL 返回 404，这与已经确认的 URL 策略冲突。应改为：

- 已发布 Slug 默认不可修改；
- 特殊修改时保存旧 Slug；
- 旧 Slug 301 到新 Slug，或作为 alias 解析；
- 评论、点赞和统计关联稳定 `post_id`，不关联当前 Slug。

### 10. 经济页不能继续作为公开财务数据源

经济页第一版已经确定为完全私有。因此 `Economy Plan` 只服务个人规划，`/economy` 必须受管理员会话保护，匿名用户不能读取收入、存款、投资、支出和备注。

如果将来需要公开展示进度，应另建脱敏数据源，不能直接把私人 Notion 数据库暴露出去。

### 11. 历史文章缺少唯一权威来源

旧文章同时存在于 Supabase、`src/content/`、内嵌内容和 Markdown 文件中。必须为每篇文章指定唯一权威来源：

- 新文章：Notion；
- 要保留的历史文章：迁移到 Notion；
- 需要特殊格式的文章：暂留本地 Markdown，但不能与 Notion 同时服务同一个 URL；
- 旧数据库只作为迁移输入，迁移后不再读取。

### 12. 任务状态和依赖图不可信

当前任务板写“规划完成”，但架构和鉴权仍是草案，D2/D3 未决，T0 又被凭证准备阻塞。`待开工` 在协作规范中代表依赖已经满足，这与现状不符。

建议分开记录四种状态：

- 产品决策：已确认 / 待确认；
- 技术前置：已完成 / 阻塞；
- 工单：待开工 / 进行中 / 待验收 / 已验收；
- 交付证据：是否齐全。

### 13. 备份不应提交到仓库

完整数据库备份可能含评论、邮箱、IP、私人财务数据和其他敏感信息。建议把完整备份放在仓库外的安全位置，仓库内只保存：

- 迁移清单；
- 迁移前后行数；
- 校验哈希；
- 不含敏感内容的验证记录。

### 14. 文档路径和索引已经漂移

当前文档仍引用不存在的文件，例如 `05-验收清单.md`、`02-目标架构与Notion-CMS设计.md`、`03-权限管理方案.md`。`docs/README.md` 还列出不存在的 `data-model.md`，同时漏列 T6。应在开工前统一所有路径和目录索引。

### 15. AdSense 条目混入了未经证实的硬门槛

“20-30 篇文章”“每篇 500 字”“域名满 6 个月”“稳定自然流量”可以作为内部运营目标，但不应写成 Google 的固定审核保证。计划应改为：遵守当前政策，确保原创、有价值、可访问、版权清晰，并准备 Privacy、About、Contact、清晰导航和站点质量基础。

## 三、建议采用的调整版计划

### M0：决策冻结

修订计划文档，固化本评审中已经确认的边界：

- `openblog` 是唯一正式代码仓库；
- `portfolio origin/main` 是迁移基线；
- 视觉和组件按白名单迁移；
- 经济页第一版完全私有；
- 已发布 Slug 默认不可修改，特殊修改保留 301/alias；
- 互动数据使用稳定文章 ID；
- 所有公开写入经过服务端 API；
- Notion API 版本和 Next.js 缓存模型在实现前重新核验。

仍需单独确认：

- `/roadmap` 是否保留；
- `/project-logs/[id]` 是否保留；
- `workflow_*` 表是否保留；
- 历史文章全部迁移到 Notion，还是保留一部分本地 Markdown。

### M1：旧仓库只读审计与视觉基线

以 `portfolio origin/main` 建立迁移清单：

- 页面和旧 URL 清单；
- 组件、CSS、主题和静态资源清单；
- 依赖闭包；
- 文章、评论、点赞、留言、项目、任务和日程数据来源；
- 生产站点页面截图基线。

初步允许迁移：`globals.css`、必要的 UI 组件、首页视觉组件、导航、主题系统和确认保留的静态资源。

明确不迁移：AI 写作助手、Tiptap、Prisma、通用 Supabase 代理、旧鉴权实现和示例 seed 数据。

### M2：openblog 项目初始化

在 `openblog` 新建可运行的 Next.js App Router 项目，锁定 Node、包管理器、Next.js、React、Tailwind 和依赖版本，建立：

- `package.json` 与锁文件；
- `src/`；
- TypeScript、Tailwind、ESLint 和 Next 配置；
- `supabase/migrations/`；
- 环境变量启动校验；
- 首页、博客列表、文章详情和后台占位页。

完成后先通过本地启动、构建和视觉截图，再进入数据迁移。

### M3：安全基线

将旧站安全处置和新站安全实现分开：

- 新站实现密码哈希、HMAC 会话、安全 Cookie、登录限流和 fail-fast 环境变量校验；
- 服务端与客户端 Supabase client 分离；
- 不建立通用任意表代理；
- 删除危险接口设计；
- 为公开写入增加输入校验、HTML 清洗、限流和待审核状态；
- 轮换曾经泄露的 GitHub token，并检查旧仓库历史。

管理员密码应由所有者本地生成和配置，不通过聊天发送给 agent。

### M4：Supabase 数据层

先设计 schema，再迁移数据。候选表包括：

- `comments`、`likes`、`guestbook`、`friend_links`；
- `projects`、`tasks`、`schedules`、`activity_log`；
- `project_logs`，仅在确认页面保留后建立；
- `workflow_*`，仅在确认路线图保留后建立。

每张表都要有唯一约束、索引、时间戳、RLS 策略、稳定文章关联键和可重复的迁移脚本。迁移前后记录行数，完整备份放在仓库外。

### M5：互动接口与管理后台

实现专用资源接口：

- 评论提交、审核、删除；
- 点赞去重；
- 留言提交和管理；
- 友链管理；
- 项目、任务、日程管理；
- 活动日志（如页面保留）。

匿名用户只能访问公开数据，管理员才能访问个人管理数据。每个接口完成输入校验、错误处理、限流和权限测试。

### M6：Notion CMS

实现 Notion 客户端、属性映射、分页、递归块渲染、文章列表和详情、归档、标签、RSS、sitemap、缓存和 Webhook 失效。

这一阶段必须同时解决：

- API 版本固定；
- Webhook verification token 和签名校验；
- Webhook 失败时的 ISR 兜底；
- Notion 图片 URL 的稳定化；
- 稳定 `post_id`；
- 已发布 Slug 不可变和旧 Slug 301/alias。

### M7：经济页和合规页

经济页只对管理员开放，读取私有 `Economy Plan`。公开访客不应看到个人收入、存款、投资、支出或备注。

同时完成 Privacy、Contact、About 内容核对，并说明 Cookie、IP 哈希、第三方服务和广告相关处理。

### M8：上线切换与最终验收

上线前完成：

- 旧 URL 对照表和重定向规则；
- 功能、数据完整性、视觉回归、缓存失效和 Webhook 测试；
- 安全、移动端和 Lighthouse 检查；
- Vercel 部署和 Search Console 配置；
- 备份恢复测试；
- 旧站回滚方案。

## 四、建议调整的验收规则

以下验收项应在后续修订时替换：

| 原规则 | 建议规则 |
|---|---|
| 修改 Slug 后旧 URL 404 | 已发布 Slug 默认不可修改；特殊修改保留 301/alias |
| 1 分钟内一定完成 Notion 同步 | Webhook 正常时触发按需失效；失败时 ISR 最终恢复，验收记录实际延迟 |
| 匿名 Supabase 直接 INSERT | 匿名写入统一经过服务端 API，数据库只接受服务端写入 |
| 经济页公开展示 Notion 规划 | `/economy` 仅管理员可见，公开访客无权读取 |
| AdSense 20-30 篇、每篇 500 字、域名 6 个月 | 作为内部运营目标，不作为官方硬性保证 |
| 完整备份放 `MIGRATION-BACKUP/` | 完整备份放仓库外，仓库只保留校验和迁移记录 |

## 五、执行顺序建议

1. 先修订计划文档和失效引用。
2. 冻结页面范围、历史文章来源和数据字段映射。
3. 以 `portfolio origin/main` 完成只读迁移清单和视觉截图基线。
4. 在 `openblog` 初始化最小可运行应用。
5. 完成安全基线和 Supabase schema。
6. 迁移数据并实现互动接口。
7. 接入 Notion CMS。
8. 最后实现私有经济页、合规页和上线切换。

在 M0 和 M1 完成前，不应执行现有 T0/T1 中针对旧仓库路径的删除操作。

- 所有文件路径是否真实存在；
- 工单执行对象是否为 `openblog`；
